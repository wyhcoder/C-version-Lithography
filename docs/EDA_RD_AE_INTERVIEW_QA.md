### 1.2 当前项目用到的技术

- C++20：主体实现与模块组织。
- Eigen：矩阵、向量、SVD、LDLT。
- FFTW：二维 FFT/IFFT。
- OpenCV：图像读取、轮廓、连通域、距离变换。

### 1.3 面试中必须诚实说明的边界

当前项目具备计算光刻核心原型，但还不能称为工业级 OPC 产品：

- 输入主要是 BMP/TXT/NPY，而不是层次化 GDSII/OASIS 版图数据库。
- 当前成像是标量投影模型，不是完整高 NA 矢量成像或严格掩模电磁模型。
- 光刻胶使用 sigmoid 近似，不是经过真实晶圆数据标定的完整胶模型。
- MEEF 当前把 x/y 位移分开求解，SRAF 在主控制点优化时保持固定。
- CMake 中尚未接入系统化 CTest；测试和 CI 是明显改进项。
- `config.yaml` 中部分真实输入仍是本机绝对路径，若交付给客户需改成可移植数据包。
- 若干旧 demo 仍存在硬编码路径，主 MEEF demo 的可移植性更好，但整个仓库尚未完全统一。

面试时主动说出这些边界不是减分。能够区分“已经实现”“验证过”“计划改进”，通常比把原型包装成产品更可信。

## 2. 项目介绍与通用问题

### Q1：请用 30 秒介绍这个项目。

**参考回答：**

这是一个用 C++20 实现的计算光刻和 OPC 优化原型。项目从光源、光瞳、掩模和光刻胶参数出发，通过 Abbe 或 SOCS 方法计算 aerial image 和 wafer image，并实现了 CTM、Level Set、MEEF 控制点优化，以及 EPE、WEPE、PE 和 PV Band 评价。工程上使用 Eigen、FFTW、OpenCV、OpenMP、yaml-cpp 和 CMake，重点解决了成像缓存、数值求解、多线程和实验可复现问题。

### Q2：如果面试官给你 1 分钟，怎样突出个人贡献？

**参考回答：**

我不只运行了已有 demo，而是沿着“配置—成像—误差—优化—保存结果”的调用链理解和改进项目。以 MEEF 为例，我梳理了每个控制点 `x+、x-、y+、y-` 四次扰动如何形成灵敏度矩阵，理解了 SVD 截断、Tikhonov 正则化和 L-Curve 选参；工程上还处理了 OpenMP 嵌套并行、FFTW 线程私有缓冲、YAML 参数化、配置快照、Python 控制点导入和构建路径问题。我的重点是让算法不仅“能跑”，还可以解释、复现和排查。

回答时应把“我真正做过的部分”换成自己的真实经历，不要把整个仓库都说成独立完成。

### Q3：项目的核心模块如何划分？

**参考回答：**

可以分成四层：

1. 参数和物理对象层：`SimulationParameters`、`Grid`、`Source`、`Pupil`、`Mask`。
2. 成像层：`LithoPrepare` 生成 `ImagingCache`，`Imaging::compute()` 执行 FFT 成像和胶模型。
3. 指标与几何层：`Loss`、`EpSelect`、`PvbandComputer`、MSAA 和参数曲线渲染。
4. 优化层：`CTM_Optimizer`、`LSM_Optimizer`、`MEEF_Optimizer`。

公共实现编译成 `litho_core` 静态库，各个 demo 只提供入口和参数组织。

### Q4：为什么把 `LithoPrepare` 和 `Imaging` 分开？

**参考回答：**

固定光学条件下，光源采样、频移光瞳和 SOCS 分解不会随 mask 每轮变化。如果每次优化都重复计算，成本很高。`LithoPrepare` 把这些量预计算到 `ImagingCache`，`Imaging` 每次只处理新 mask 的 FFT、与各光学核相乘、IFFT 和强度累加。这样既节省时间，也让 CTM、LSM、MEEF 等模块复用同一套成像数据。

### Q5：`ImagingCache` 里哪些量可以缓存，哪些不能？

**参考回答：**

在 NA、波长、像差、光源和网格固定时，可以缓存频率网格、光瞳、光源点和权重、频移光瞳、SOCS 核及特征值。mask 频谱、电场、aerial image 和 wafer image 随 mask 改变，不能作为跨迭代固定缓存。若 focus、dose 或像差改变，也要区分：dose 可能只改变胶阈值，而 defocus 会改变 pupil/核，必须重建相应 cache。

### Q6：为什么使用 YAML，而不是把参数写死在代码里？

**参考回答：**

计算光刻参数多，硬编码难以复现和批量实验。YAML 把系统、光学、光源、光刻胶、输入路径和 MEEF 参数集中管理。主 MEEF demo 会校验必需字段、解析相对路径，并把实际配置复制到输出目录，同时保存 console log。这样结果可以追溯到具体输入和参数。

### Q7：项目从源码到可执行程序经历什么？

**参考回答：**

```text
CMakeLists.txt
   -> CMake 配置并查找 Eigen/FFTW/OpenCV/yaml-cpp/OpenMP
   -> Make 或 Ninja 调用编译器，把 .cpp 编译为 .o
   -> 链接出 liblitho_core.a
   -> 再链接各个 demo 可执行文件
```

项目使用 target-based CMake。`litho_core` 通过 `PUBLIC` 传播必要的头文件目录和依赖，demo 链接它后即可使用公共模块。

### Q8：为什么项目要求从 `build-release` 目录运行主 MEEF demo？

**参考回答：**

当前主 demo 把当前工作目录当作 build 目录，并从其中读取 `config.yaml` 和 `target_pattern/`，再把父目录当作项目根。CMake 在配置阶段用 `configure_file` 和 `file(COPY ...)` 把这些资源复制到 build 目录。所以修改根 YAML 或新增目标图片后，需要重新执行 CMake 配置；只重新编译不一定刷新资源。

更工业化的改进是显式传入工作目录或资源根路径，不依赖启动位置推断。

## 3. 光刻成像与领域知识

### Q9：Abbe 成像的基本思想是什么？

**参考回答：**

把部分相干光源离散为多个光源点。对每个光源点，mask 频谱与对应的频移光瞳相乘，IFFT 得到复电场，然后取模平方。不同光源点彼此非相干，所以累加的是强度：

```text
I(x,y) = sum_s w_s * |IFFT(M(f,g) * H_s(f,g))|^2 / sum_s w_s
```

项目中 mask 的 FFT 每次只算一次，各个核共享它。

### Q10：为什么不能把不同光源点的电场直接相加？

**参考回答：**

不同非相干光源点之间没有固定相位关系，应分别取强度后相加。如果先把复电场相加再取模平方，会产生不应存在的交叉干涉项。同一相干模式内部可以累加复振幅，不同非相干模式之间累加强度。

### Q11：SOCS 是什么，为什么可以加速？

**参考回答：**

SOCS 把部分相干成像算子分解为少量相干核：

```text
I(x,y) ~= sum_k lambda_k * |IFFT(M * K_k)|^2
```

项目把加权的频移光瞳组成矩阵并做薄 SVD，保存前若干个模式。若相干核数 `K` 远小于光源点数 `Ns`，每次成像的 IFFT 数量就从 `Ns` 降到 `K`。代价是截断误差，所以要在速度和精度间权衡。

### Q12：为什么 SOCS 的权重是奇异值平方？

**参考回答：**

SVD 中奇异值描述振幅算子在该模式上的尺度，而最终强度是复振幅模平方，因此强度权重对应 `sigma_k^2`。代码把这些值放在 `ImagingCache::socs_vals` 中。

### Q13：怎样选择 SOCS 模态数？

**参考回答：**

不能只看“保留了多少奇异值能量”。我会在代表性图形和工艺条件上扫描 `K`，同时比较：

- 与 Abbe 基准的 aerial RMS/max error；
- wafer mismatch、EPE 和 PV Band；
- runtime 和内存；
- 不同图形上的最坏误差。

最后选择满足精度验收线的最小 `K`。如果只在一个简单图形上选 `K`，可能对复杂 hotspot 失效。

### Q14：当前代码如何区分 Abbe 和 SOCS？

**参考回答：**

`Imaging::compute()` 通过 `socs_vals` 是否为空区分：SOCS 模式为每个核保存一个非负特征值，Abbe 模式则使用 `source_ws`。它还检查核数量和权重数量是否一致。这比根据“核数是否等于光源点数”推断更稳健。

需要注意，`PvbandComputer::_backpropagate()` 中仍有基于 `K == source point count` 的判断，这是代码审查时值得继续统一的地方。

### Q15：`fftshift` 和 `ifftshift` 为什么容易出错？

**参考回答：**

数学推导通常把零频放在矩阵中心，而 FFTW 的直接输出把零频放在角点。mask 频谱与 pupil 核相乘时必须采用同一布局，否则会出现相位错位、空间平移或镜像。奇偶尺寸的 shift 也可能不同，因此要用 delta、常数、单频正弦以及奇数/偶数矩阵做往返测试。

### Q16：项目中的光刻胶模型是什么？

**参考回答：**

项目用 sigmoid 把 aerial image 转为连续 wafer image：

```text
W = 1 / (1 + exp(-alpha * (I - threshold)))
```

`threshold` 控制显影阈值，`alpha` 控制边缘陡峭程度。它适合可微优化和算法验证，但不能等同于经过工艺标定的完整化学放大型光刻胶模型。`alpha` 太大还可能造成梯度集中和指数数值问题。

### Q17：NA、波长和 sigma 对结果有什么影响？

**参考回答：**

- 更短波长和更高 NA 通常提升可传递空间频率和分辨率。
- 更高 NA 往往也让景深更敏感，并增加矢量效应的重要性。
- `sigma_in/sigma_out` 描述归一化光源形状，改变照明相干性和方向选择性。
- 这些参数共同影响分辨率、对比度、工艺窗口和特定图形的可印刷性。

回答时不要只背 Rayleigh 公式，还要说明成像质量取决于图形方向、照明形状和工艺条件。

### Q18：Zernike 多项式在项目里做什么？

**参考回答：**

Zernike 多项式在单位圆光瞳上描述像差。`Pupil` 把各阶系数组合成 wavefront，再通过 `exp(i*2*pi*phase)` 写入复光瞳。PV Band 的 defocus 扫描会改变相应像差并重建光学 cache。面试时还应说明不同 Zernike 编号约定可能不同，必须明确单位、归一化和索引规范。

### Q19：为什么只看二值 wafer 图不够？

**参考回答：**

阈值化会隐藏连续 aerial image 的差异。两个模型可能在阈值同侧得到相同二值结果，但 aerial slope 已明显不同，换一个 dose/focus 就会分叉。因此验证至少要同时看 aerial error、wafer error、EPE 和 process window，不能只看一张二值图“像不像”。

### Q20：当前项目为什么不能直接称为高 NA 完整模型？

**参考回答：**

当前主线是标量成像：一个复光瞳、标量 mask 和标量电场强度。真正高 NA 产品通常要考虑偏振、矢量电场分量、掩模 3D 电磁效应、材料和更完整的工艺模型。这个项目可以作为算法和软件架构原型，但面试时不能把标量 SOCS 说成完整矢量成像。

## 4. OPC、EPE、MEEF 与优化

### Q21：什么是 OPC？

**参考回答：**

OPC 是对 mask 图形主动做边缘偏置、角部修正或添加 SRAF，使其经过光学衍射和光刻胶非线性后，wafer 轮廓更接近目标。数学上它是带工艺模型和制造约束的逆问题，既追求 nominal 精度，也要考虑 process window 和 mask 可制造性。

### Q22：PE、EPE 和 WEPE 有什么区别？

**参考回答：**

- PE：全图 wafer 与 target 的平方像素误差，覆盖全局区域。
- EPE：在 evaluation point 处估计边缘位置误差，更接近轮廓签核。
- WEPE：对特定 EP 加权，突出线端、拐角或关键弱点。

当前 `Loss::evaluate_epe()` 使用局部线性近似：

```text
EPE ~= |I - threshold| / |grad(I)| * pixel_size
```

它返回逐点 EPE 和总和，`weighted_epe()` 再计算加权和。

### Q23：这个 EPE 公式有什么假设和局限？

**参考回答：**

它假设阈值轮廓附近 aerial image 可以一阶线性化，误差等于强度差除以局部斜率。当 `|grad(I)|` 很小、EP 不在正确法向上、轮廓拓扑改变或边缘离 EP 太远时，近似可能不稳定。代码加了 `1e-12` 防止除零，但数值不爆炸不代表物理上可靠。工业验证还应与显式轮廓求交或签核工具对照。

### Q24：MEEF 矩阵是什么？

**参考回答：**

这里的 MEEF 矩阵表示各 EP 的 EPE 对 mask 控制点位移的局部灵敏度：

```text
Mx(i,j) = d EPE_i / d x_j
My(i,j) = d EPE_i / d y_j
```

行对应 EP，列对应主图形控制点。它把非线性的 OPC 问题在当前状态附近线性化，用于求下一步控制点移动。

### Q25：当前项目怎样构建 MEEF 矩阵？

**参考回答：**

对每个控制点创建四个任务：`x+、x-、y+、y-`。每个任务移动一个控制点、重新渲染主图形、叠加固定 SRAF、执行光刻成像并计算所有 EP 的 EPE，最后用中心差分：

```text
dE/dx ~= (E(x+delta) - E(x-delta)) / (2*delta)
```

所以一次构建约需要 `4 * 控制点数` 次成像，是主要性能热点。

### Q26：为什么使用中心差分？

**参考回答：**

函数足够光滑时，前向差分的截断误差通常是一阶 `O(delta)`，中心差分是二阶 `O(delta^2)`，精度更高。代价是每个方向需要正负两次仿真。实际效果还会受栅格、MSAA、轮廓提取和浮点误差影响。

### Q27：差分步长 `delta` 怎样选？

**参考回答：**

太大时破坏局部线性假设；太小时会被浮点误差、控制点坐标舍入、MSAA 量化和轮廓跳变淹没。我会做 step-size study，例如按数量级扫描 `delta`，观察 MEEF 每列的方向、范数和最终更新是否稳定，并用代表性控制点做正负扰动曲线。

### Q28：为什么 MEEF 线性系统会病态？

**参考回答：**

相邻控制点对各 EP 的影响可能高度相似，导致矩阵列相关；某些控制点对已选 EP 几乎不可观测；EP 采样和数值差分还会带来噪声。因此小奇异值方向会把微小 EPE 误差放大成很大的控制点移动，直接求逆不稳定。

### Q29：当前代码如何求控制点位移？

**参考回答：**

当前实现先对 MEEF 矩阵做 thin SVD，按奇异值平方的累计能量保留前 `k` 个方向；再使用 Tikhonov 滤波：

```text
delta = V_k * diag(s / (s^2 + lambda)) * U_k^T * (-e)
```

`lambda` 通过 L-Curve 选取，在残差范数 `||M*delta+e||` 和解范数 `||delta||` 之间折中。x、y 两个方向当前分别求解。

### Q30：L-Curve 的直觉是什么？

**参考回答：**

正则很弱时，残差小但解范数可能很大，容易追噪声；正则很强时，解很小但拟合差。把两者画在双对数坐标上通常形成 L 形，拐角附近代表两者相对平衡。当前实现扫描 `10^-6` 到 `10^2` 的候选并用离散曲率找拐点。

需要补充：L-Curve 是启发式方法，曲线不明显时可能不稳，还应检查 lambda 边界、残差和实际目标是否改善。

### Q31：为什么 `EPE` 降低不一定代表 OPC 更好？

**参考回答：**

nominal 条件下 EPE 降低，可能伴随 mask 边缘过度复杂、最小间距违规、SRAF 可印刷、process window 变差或其他图形退化。更完整的目标应联合 nominal EPE、PV Band、MRC/DRC、mask complexity 和 hotspot 指标。

### Q32：CTM、LSM 和 MEEF 的区别是什么？

**参考回答：**

| 方法 | 优化变量 | 优点 | 局限 |
|---|---|---|---|
| CTM | 连续 mask 像素 | 梯度规则、实现直接 | 变量多，可制造性弱 |
| LSM | 隐式轮廓的符号距离函数 | 能自然演化形状和拓扑 | 数值 PDE、重初始化和稳定性更复杂 |
| MEEF | 参数曲线控制点 | 变量少、可解释、接近边缘移动 | 局部线性近似，依赖 CP/EP 选择 |

项目中 LSM 用 WENO/Godunov 形式计算演化项，MEEF 则用 MSAA 渲染控制点曲线。

### Q33：为什么主图形优化时 SRAF 保持固定？

**参考回答：**

当前 MEEF 变量只定义为主图形控制点，因此每次扰动重新渲染主图形，再叠加固定 SRAF。这样维度较小，矩阵含义清晰。若把 SRAF 位置、宽度或长度也作为变量，就要扩大灵敏度矩阵，并加入 keep-out、最小宽度/间距、不可印刷等约束。

### Q34：当前提前停止条件是什么？有什么改进？

**参考回答：**

当最大控制点位移 `|d|max` 连续 `patience` 轮小于 `step_tol` 时停止。它能避免单轮偶然小步长导致误停，但只看步长仍可能在坏的局部状态停下。可同时检查目标函数相对改善、约束违例、线性模型预测与真实改善比例，并加入 trust region 或 line search。

### Q35：什么是 PV Band？

**参考回答：**

在多个 dose/focus 工艺角下得到 wafer 图，对每个像素取最大值减最小值，形成 process variation band。PV Band 越大，说明结果对工艺变化越敏感。nominal EPE 反映标称准确度，PV Band 反映鲁棒性，两者要一起看。

### Q36：PV Band 梯度为什么难？

**参考回答：**

逐像素 `max/min` 在获胜工艺角切换处不可微。当前实现记录每个像素的 max/min winner，并对获胜 corner 使用确定的 hard max/min 次梯度。替代方案包括 smooth max/min，例如 log-sum-exp，但会引入平滑参数和近似误差。无论哪种都要做 finite-difference gradient check。

## 5. R&D：C++、数值计算与高性能问题

### Q37：`Imaging` 为什么禁止拷贝？

**参考回答：**

`Imaging` 持有 FFTW buffer 和 plan 裸句柄。如果允许默认浅拷贝，两个对象会指向同一资源，析构时产生 double free。当前头文件已经显式删除拷贝构造和拷贝赋值。进一步可以用带自定义 deleter 的智能指针或独立 RAII wrapper 封装 FFTW 资源。

### Q38：`Imaging` 保存 `const ImagingCache&` 有什么要求？

**参考回答：**

引用不拥有对象，`ImagingCache` 必须比 `Imaging` 活得更久。项目通常先构造 `LithoPrepare`/cache，再在相同作用域中构造 `Imaging`。这种设计避免复制大缓存，但需要清晰的生命周期约定。跨线程或跨异步任务时尤其要防止悬空引用。

### Q39：构造函数中分配多个 FFTW 资源，如何保证异常安全？

**参考回答：**

当前 `Imaging` 在 buffer 或 plan 创建失败时会手动释放已经成功创建的资源，避免泄漏。但手写清理路径容易遗漏。更稳健的做法是每项资源一创建就放入 RAII wrapper，这样后续步骤抛异常时由局部对象自动清理。

### Q40：为什么 MEEF 外层并行时关闭 Imaging 内层并行？

**参考回答：**

若外层控制点任务开 `T` 个线程，每个任务内部的核循环又开 `T` 个线程，可能形成近似 `T*T` 的过度订阅，增加上下文切换和缓存竞争。`Imaging::compute()` 用 `omp_in_parallel()` 判断是否已经处于并行区：外层并行时，内层不再创建线程组。

### Q41：当前 OpenMP 调度为什么有 static 和 dynamic 两种？

**参考回答：**

光学核计算的任务形状相近，使用 `schedule(static)` 可以降低调度开销。不同控制点扰动可能因曲线渲染、轮廓和数据分布产生耗时差异，MEEF 外层使用 `schedule(dynamic, 1)` 改善负载均衡。是否真的更快要用实际 workload benchmark，不能只凭经验。

### Q42：FFTW 多线程执行有哪些风险？

**参考回答：**

plan 创建阶段和执行阶段的线程安全要求不同。当前 MEEF 在进入并行区域前串行创建每个 worker 的 `Imaging`；执行共享 plan 时，每个线程使用独立输入/输出 buffer。必须避免多个线程写同一 buffer，也要核对 FFTW 官方线程安全约定。若使用 wisdom 或 `FFTW_MEASURE`，还要考虑初始化成本和并发 planner。

### Q43：为什么并行结果可能与单线程有微小差异？

**参考回答：**

浮点加法不满足严格结合律，不同归约顺序会产生舍入差异。当前成像先并行计算每个核的电场，再固定按 `k` 顺序串行累加强度，有利于单/多线程可复现。测试仍应使用绝对和相对容差，而不是要求所有 bit 完全一致。

### Q44：怎样验证 FFT 和频率坐标实现？

**参考回答：**

我会分层验证：

1. 小矩阵与 NumPy FFT 对照。
2. 检查 `ifft(fft(x)) ~= x`。
3. 检查 Parseval 能量关系。
4. 用 delta、常数和单频正弦测试频谱位置。
5. 单独测试奇数/偶数尺寸的 shift 往返。
6. 最后才比较 Abbe/SOCS 完整图像。

从底层开始可以快速区分“FFT 归一化错误”“shift 错误”和“光学核错误”。

### Q45：怎样做梯度检查？

**参考回答：**

随机选少量变量，用中心差分计算数值梯度，与解析/反向梯度比较：

```text
g_num(i) = [L(x+h*e_i) - L(x-h*e_i)] / (2h)
```

误差指标可用：

```text
||g_num-g_ana|| / max(1, ||g_num||, ||g_ana||)
```

要扫描多个 `h`，避开 sigmoid 饱和和 max/min 切换点。只测试一个步长可能把截断误差或舍入误差误认为梯度错误。

### Q46：MEEF 构建的复杂度怎样估算？

**参考回答：**

设控制点数为 `C`、SOCS 核数为 `K`、网格为 `N*N`，每轮 MEEF 约需 `4C` 次成像，每次包含一个 mask FFT 和 `K` 个核 IFFT，主要复杂度近似：

```text
O(C * K * N^2 log N)
```

完整优化再乘迭代数。内存主要包括 `K` 个复电场、光学核和每线程 buffer。实际瓶颈要用 profiler 确认，因为渲染、EPE 和 I/O 也可能占比明显。

### Q47：如何正确做性能测试？

**参考回答：**

- 固定 YAML、输入图形、SOCS 核数和运行模式。
- 使用 Release 或 RelWithDebInfo，不与 Debug 混比。
- 排除 GUI 等待和不必要 I/O。
- 测 1/2/4/8 线程，每组预热并重复多次，报告中位数。
- 同时报 wall time、CPU time、峰值内存、speedup 和 efficiency。
- 检查不同线程数的数值结果仍在容差内。
- macOS 用 Instruments，Linux 用 `perf`；先测量再决定优化方向。

### Q48：你会怎样减少 MEEF runtime？

**参考回答：**

优先级应由 profiling 决定，可能的方向包括：

1. 减少不必要的控制点或自适应选择高误差区域。
2. 选择满足精度的最小 SOCS 核数。
3. 缓存不随单点扰动变化的数据，减少反复分配。
4. 优化 OpenMP 任务粒度和 NUMA/线程绑定。
5. 降低每轮全量结果 I/O。
6. 探索伴随法/解析梯度，避免每个变量四次前向仿真。

不能直接回答“多开线程”，因为算法复杂度、内存带宽和过度订阅可能才是限制。

## 6. R&D：工程化、测试与代码审查问题

### Q49：这个项目最应该补哪些测试？

**参考回答：**

优先补以下测试并接入 CTest：

1. FFT/shift 小矩阵单元测试。
2. Source 权重非负、非空和归一化测试。
3. Abbe 与 SOCS 的 golden regression。
4. EPE 已知直线/矩形案例和坐标方向测试。
5. MEEF 中心差分和小型病态矩阵求解测试。
6. PV Band corner 和梯度检查。
7. 单线程/多线程一致性。
8. YAML 缺字段、非法路径和非法参数。
9. ASan/UBSan，以及单独的 TSan 配置。

### Q50：如果 C++ 结果和 Python 不一致，你怎么排查？

**参考回答：**

我会先固定最小输入和所有参数，然后逐层保存中间量：网格、source map、pupil、shifted pupil、mask FFT、单个核电场、aerial image、wafer image、EP 和最终 loss。每层比较 shape、dtype、坐标顺序、单位、归一化、shift 和误差。定位到第一层不一致，而不是只看最终图。

这个项目还要特别检查 `(y,x)` 与 `(x,y)`、FFTW IFFT 的 `1/N^2` 归一化、BMP padding、阈值/alpha，以及 Python object-array 控制点转换。

### Q51：怎样设计一个可复现的数值实验？

**参考回答：**

输出包至少包含：实际配置快照、输入文件校验值、代码版本/commit、编译类型、依赖版本、线程数、随机种子、console log、阶段计时和关键结果。主 MEEF demo 已保存 YAML 快照与日志，但若做产品化，还应记录构建信息和输入 hash。

### Q52：如何处理非法配置和输入？

**参考回答：**

遵循 fail fast：启动时校验字段存在、类型、取值范围、文件存在性、矩阵尺寸和数据有限性；错误信息要包含字段名、实际值和预期范围。不要让错误输入进入长时间优化后才崩溃。主 MEEF demo 已对 mode、路径和文件名做了一部分检查。

### Q53：怎样审查一个拥有 FFTW 资源的类？

**参考回答：**

我会检查：初始化失败是否泄漏、析构是否允许空句柄、是否禁止浅拷贝、是否支持/需要移动、引用成员生命周期、线程并发执行规则、buffer 尺寸溢出、plan 与输入尺寸是否一致，以及异常发生后对象是否仍满足不变量。

### Q54：项目当前最明显的工程短板是什么？

**参考回答：**

我会选“自动化验证不足”作为首要短板。现在有多个 demo 和已有 build 产物，但顶层 CMake 没有正式测试目标。数值软件最怕静默回归，所以应该先建立小规模 golden tests、梯度检查、Sanitizer 和 CI，再做更激进的性能重构。

### Q55：如果让你把它向工业 EDA 推进一步，你会怎么做？

**参考回答：**

分阶段推进：

1. 先建立 correctness baseline：Python/Abbe golden、CTest、CI 和误差规范。
2. 统一路径、配置、日志、错误码和可安装包，消除 demo 硬编码。
3. 引入 GDSII/OASIS、多边形布尔、层次结构、tile/halo 和空间索引。
4. 加入 MRC/DRC、SRAF 约束和多工艺角目标。
5. 用真实标定数据验证模型，并建立容量和性能回归。

这是“验证—工程化—版图规模—工艺能力”的顺序，不应一开始就盲目扩展功能。

## 7. AE 岗位高频问题与场景题

### Q56：你为什么也适合 AE，而不只是 R&D？

**参考回答：**

这个项目让我同时接触算法和落地问题。我能解释 SOCS、EPE、MEEF 等原理，也做过 YAML 参数、数据格式、Python/C++ 对齐、构建环境和运行日志排查。AE 的价值不是只会演示软件，而是能把客户现象转换成可复现技术问题，再和 R&D 一起推进闭环。我愿意面对客户，同时保留代码级分析能力。

### Q57：你理解的 EDA AE 日常工作是什么？

**参考回答：**

AE 连接客户和产品/R&D，常见工作包括：需求澄清、工具部署、flow 搭建、参数调优、benchmark、结果解释、问题复现、培训、现场支持和反馈产品需求。衡量标准不仅是“问题回答了”，还包括客户是否能稳定复现、结果是否达到验收线、风险是否及时升级。

### Q58：客户说“你们结果不准”，你第一步做什么？

**参考回答：**

先把“不准”变成可测量定义，而不是立刻调参：

- 比较对象是什么版本和什么工艺条件？
- 指标是 aerial RMS、CD、EPE、PV Band 还是某个 hotspot？
- 输入版图、层、单位、坐标、bias 是否一致？
- dose/focus、NA、sigma、像差和 resist 参数是否一致？
- 问题是全局偏差、局部图形偏差还是随机不稳定？

然后建立最小复现，逐层比较中间结果，定位是输入、配置、模型、数值实现还是验收口径问题。

### Q59：客户说“运行太慢”，你怎样处理？

**参考回答：**

先确认容量、版本、机器、线程数、运行模式和耗时阶段，区分初始化、模型生成、核心计算、I/O 和可视化。给出短期和长期两层方案：短期可减少调试输出、合理设置线程、复用 cache、选择合适 SOCS 核数；长期由 profiling 结果推动 R&D 优化。任何提速都必须同步验证精度，不能偷偷降低模型等级。

### Q60：客户环境能编译，你本机不能；或者反过来，怎样排查？

**参考回答：**

收集操作系统和架构、编译器/CMake、依赖版本、生成器、完整配置日志和第一条错误。再检查 `CMakeCache.txt` 是否残留旧路径，`compile_commands.json` 中真实 include/link 参数，以及运行期动态库。构建问题要区分配置、编译、链接和运行四个阶段，不能只把最后几十行日志转给 R&D。

### Q61：客户只能提供敏感数据，怎样处理？

**参考回答：**

遵守公司和客户的数据分级、传输、存储、访问和销毁流程；未经授权不复制到个人设备或公共服务。优先让客户生成脱敏最小案例，或在获批环境中现场复现。问题单只记录必要元数据和可公开日志。技术便利不能越过数据安全边界。

### Q62：怎样定义一次 benchmark 的验收标准？

**参考回答：**

在运行前与客户确认：数据集范围、golden 来源、模型/工艺条件、精度指标、runtime/内存、硬件、线程数、失败判定和结果报告格式。精度与性能必须同时固定条件。若中途更改参数或数据集，要明确标记为新实验，不能挑选最好结果替代原验收。

### Q63：客户给出一个 hotspot，你怎样建立最小复现？

**参考回答：**

从原版图裁出能保留现象的最小窗口，同时保留必要 halo、层信息和工艺参数；记录裁剪前后结果，确保问题仍存在。然后逐步简化 source、pupil、resist 或优化步骤，找到最早出现差异的阶段。若裁剪后问题消失，说明可能存在长程光学影响、层次上下文或边界处理问题，不能强行用过小 testcase。

### Q64：如果客户参数设置明显不合理，你怎么沟通？

**参考回答：**

先说明观察到的现象和证据，再解释参数的物理/数值影响，最后给出可验证的对照实验。例如：“当前 `delta` 太小可能被栅格和 MSAA 量化淹没；建议保持其他条件不变，扫描三个步长并比较 MEEF 列稳定性。”避免只说“你的参数错了”，也不要在未验证时承诺某个值一定最好。

### Q65：销售已经向客户承诺了尚未支持的功能，怎么办？

**参考回答：**

先内部确认真实能力、可行替代和研发成本，然后尽快统一对外口径。向客户清晰区分当前支持、workaround、计划功能和时间风险，不伪造结果。AE 应推动需求优先级和验收标准，但不能代替 R&D 随意承诺交付日期。

### Q66：现场问题暂时无法解决，怎样避免客户失去信任？

**参考回答：**

先给出已确认事实、影响范围、临时规避方案和下一次更新时间；同步收集完整复现包并明确 owner。后续即使没有最终答案，也按约定更新排查进展。客户最难接受的通常不是复杂问题本身，而是没有边界、没有负责人、没有时间点。

### Q67：怎样把客户问题写成高质量 R&D issue？

**参考回答：**

一个好 issue 应包含：

- 客户影响和优先级；
- 版本、平台、硬件和依赖；
- 最小输入与配置；
- 精确执行命令；
- 期望结果与实际结果；
- 完整日志和首次异常位置；
- 是否可稳定复现；
- 已排除项和 workaround；
- 数据访问限制。

目标是让 R&D 不需要反复追问基础信息，就能开始定位。

### Q68：如何给非算法背景客户解释 SOCS？

**参考回答：**

我会说：“精确方法需要分别计算很多照明点，SOCS 把这些重复影响压缩成少量最重要的成像模式，因此明显减少计算量。模式越多越接近精确结果，但运行更慢。我们会用客户关心的 EPE/CD 和 runtime 一起选择模式数。”先讲价值和取舍，再根据对方需要补数学细节。

### Q69：如何给客户解释“nominal 更好但 PV Band 更差”？

**参考回答：**

可以类比为“一个方案在标准条件下瞄得很准，但对环境变化更敏感”。nominal EPE 只测一个工艺点，PV Band 测 dose/focus 波动下的稳定性。不能只挑一个指标，要根据量产目标在标称精度和工艺鲁棒性间选择。

### Q70：客户要求一个你认为不合理的优化结果，怎么办？

**参考回答：**

先确认客户真正目标，也许他关心的是某个签核指标而不是算法内部 loss。用数据展示当前目标之间的冲突，例如 EPE、PV Band、MRC 和 runtime 的 trade-off，提出两到三个可比较方案并写清代价。最终决策应基于双方确认的验收标准，而不是 AE 私自改变目标。

### Q71：AE 为什么也要懂 Linux、C++ 和数值算法？

**参考回答：**

EDA 问题经常发生在远程 Linux、集群和复杂数据 flow 中。只会 GUI 很难区分配置、环境、性能和算法问题。理解 C++ 调用链、线程、动态库和数值误差，可以更快形成最小复现、提出有效 workaround，并减少 R&D 与客户之间的信息损失。

### Q72：如果客户现场不能联网，你如何准备？

**参考回答：**

提前准备离线安装包、依赖清单、校验值、license/环境检查脚本、示例数据、回滚方案、操作手册和常见错误表；确认目标 OS、架构、磁盘、内存和权限。现场所有变更要留日志。离线环境更强调准备和可恢复性，不能依赖临时下载解决问题。

## 8. 行为题与项目深挖题

### Q73：项目中最难的问题是什么？

**参考回答框架：**

不要只说“算法很复杂”，用 STAR 结构：

- Situation：MEEF 每个控制点需要多次成像，结果还要与 Python/输入数据保持一致。
- Task：既保证正确性，又让运行可复现并支持并行。
- Action：拆解调用链；逐层核对坐标、mask 尺寸和中间量；用中心差分建立矩阵；处理 OpenMP 嵌套和线程私有 FFTW buffer；把参数与结果快照落盘。
- Result：说明你真实完成并验证的结果，不要编造未测的加速比或精度数字。
- Reflection：下一步应补自动化 regression 和更完整真实数据验证。

### Q74：讲一个你定位 bug 的例子。

**参考回答：**

可以讲路径/构建问题：源码修改后用户实际仍运行旧 build 目录中的二进制，表面看代码已改但行为没变。排查时不能只看源码，要核对实际命令、当前目录、二进制时间戳/字符串、CMake cache 和重新构建日志。这个经验让我形成了“源码—构建目标—实际二进制—真实输入”四层验证习惯。

也可以讲 251×251 输入与 257×257 网格 padding 导致逐像素比较不一致，但必须明确这是尺寸/坐标对齐问题，不是模型精度问题。

### Q75：如果你和面试官对算法选择意见不同，怎么回答？

**参考回答：**

先复述双方目标和约束，再用可验证指标比较方案。例如中心差分更准但前向次数更多；解析梯度更快但实现和验证成本更高。提出小规模实验和验收标准，而不是争论“哪个算法更高级”。如果对方指出代码事实错误，应直接修正并说明影响。

### Q76：你在项目中的最大收获是什么？

**参考回答：**

我最大的收获是把物理模型、数值算法和软件工程连起来。一个公式变成代码后，还要处理坐标约定、FFT 归一化、缓存生命周期、并行数据竞争、输入格式和可复现性。EDA R&D/AE 的价值正是在这些边界处把问题做闭环。

### Q77：你目前最大的短板是什么？

**R&D 参考回答：**

我目前在工业版图数据库、真实工艺标定和超大规模分布式计算方面经验不足。我的补强计划是先把当前项目加入 GDS/OASIS 读取、tile/halo 和自动回归，再系统学习真实 OPC flow 与 model calibration。

**AE 参考回答：**

我目前真实客户现场和量产 flow 的经验有限，但我已经形成了最小复现、日志、版本和验收标准的排障方法。我会通过产品手册、内部案例、shadow support 和复盘尽快补足客户场景，同时不在不确定时过度承诺。

### Q78：为什么选择 EDA？

**参考回答：**

我喜欢 EDA 把物理、数学、算法和工程放在同一个问题里。这个项目让我看到，一个成像公式只有变成稳定、可验证、可扩展的软件，才能真正产生价值。我希望继续做这种既需要深入技术、又与芯片制造实际问题紧密相连的工作。

## 9. 面试官可能要求现场画出的图

### 9.1 Abbe 与 SOCS

```text
Abbe:
source point 1 -> shifted pupil -> IFFT -> |E1|^2 --+
source point 2 -> shifted pupil -> IFFT -> |E2|^2 --+--> weighted sum
...                                                   |
source point Ns -------------------------------------+

SOCS:
all shifted pupils -> SVD -> top K coherent kernels
                               |
mask FFT * K kernels -> K IFFTs -> weighted intensity sum
```

### 9.2 MEEF 一轮优化

```text
current control points
        |
        +--> each CP: x+ / x- / y+ / y-
        |         -> render mask -> imaging -> EPE
        |         -> central difference -> Mx, My
        |
        +--> SVD truncation + L-Curve/Tikhonov
        |         -> delta_x, delta_y
        |
        +--> update CP -> render + fixed SRAF
                  -> evaluate EPE/WEPE/PE -> next iteration
```

### 9.3 AE 排障漏斗

```text
客户现象
  -> 明确定义指标和影响
  -> 固定版本/环境/输入/配置
  -> 最小复现
  -> 找到第一层不一致
  -> workaround + 根因 issue
  -> 客户验证
  -> regression / 文档 / 产品改进
```

## 10. 面试中不要这样回答

- 不要说“这个项目已经是完整 OPC 产品”。
- 不要把 sigmoid resist 说成真实工艺已标定模型。
- 不要把标量 SOCS 说成完整高 NA 矢量/电磁成像。
- 不要声称“用了 OpenMP 就一定线性加速”。
- 不要把 demo 能运行等同于算法正确。
- 不要只展示最终 PNG，不讲输入、参数和定量指标。
- 不要背一个未经当前机器验证的加速比。
- 不要说整个项目都是自己独立完成，除非事实确实如此。
- AE 面试中不要一遇到问题就说“交给研发”；先完成信息收集、复现和影响判断。
- R&D 面试中不要只谈公式，不谈数据结构、复杂度、测试和工程边界。

## 13. 七天复习建议

### 第 1 天：项目主线

能不看文档画出 `config -> simulator -> prepare/cache -> imaging -> optimizer -> metrics`。

### 第 2 天：光刻成像

口述 Abbe、SOCS、FFT shift、光瞳、光源、sigmoid resist，并说明模型边界。

手推中心差分、MEEF 矩阵维度、SVD/Tikhonov 和 L-Curve；说明 CP、EP、EPE、WEPE。

### 第 4 天：C++ 与并行

复习 RAII、引用生命周期、Rule of Five、OpenMP schedule、过度订阅、FFTW buffer 和浮点可复现性。

### 第 5 天：测试与排障

练习 Python/C++ 不一致、旧二进制、路径、维度、坐标、依赖和性能下降的排查流程。

### 第 6 天：按岗位专项准备

- R&D：重点回答 Q24～Q55，并练习白板复杂度和测试设计。
- AE：重点回答 Q56～Q72，并练习把技术结论改写成客户语言。

### 第 7 天：模拟面试

完成：30 秒介绍、1 分钟介绍、一个难题、一个 bug、一个短板、一个岗位动机，再随机抽 15 题口述。

## 14. 最终自测标准

如果能做到下面几点，项目面试准备基本合格：

- 90 秒内讲清项目价值、数据流、个人贡献和边界。
- 不看代码写出 Abbe/SOCS 与 MEEF 中心差分公式。
- 能解释 MEEF 为什么病态，以及 SVD/Tikhonov 如何稳定求解。
- 能画出 OpenMP 外层/内层并行关系，并解释过度订阅。
- 能给出 Python/C++ 数值不一致的逐层排查顺序。
- 能说明项目当前至少五个工业化差距。
- 能分别用 R&D 和 AE 视角回答“为什么适合这个岗位”。
- 所有性能和精度数字都能指出测试条件；没有证据时明确说尚未验证。
